### D. Pipeline changes (written, NOT yet recomputed)

Two changes in `wavescripts/processor.py`:

**Change 1: `_count_interp_in_window()` (new function)**
Counts PCHIP-filled NaN samples within the analysis window per probe.
Stored in meta as `interp_in_window_{pos}`. Called in `process_selected_data` after
`run_find_wave_ranges`. This is a diagnostic column — currently NOT used for quality
flagging (see comment in `_write_quality_flags` explaining why it creates false positives).

**Change 2: Layer 2 monotone-drift detection (new `_mono_core`)**
Original spike filter required sign reversal (`rise × fall < 0`) to catch single-sample
spikes. False troughs in the 20260327 data descend at ~4.5 mm/sample MONOTONICALLY —
no sign reversal, so they escaped.

New parallel condition in `constants.py`: `CLIP.DIFF_MONO_MM = 3.5 mm/sample`.
Any neighbouring diff exceeding 3.5 mm/sample (regardless of sign) is flagged + VEL_BUFFER.
Safety margin: max physical wave velocity ≈ 0.8 mm/sample → 4× headroom at 3.5.

**Preview test (dry run, no recompute yet):**
```
run1: 92 new mono-flagged events, 148 NaN in window (3.9%)  — already dropout_critical
run2: 132 new mono-flagged events, 146 NaN in window (3.9%) — would become dropout_critical
run3:  32 new mono-flagged events,  62 NaN in window (1.7%) — stays below 2% threshold ✓
```

**What has NOT been verified:**
- Whether the new filter actually removes the visible false troughs in the quicklook signal
  (need to recompute 20260327 folder and regenerate quicklook)
- Whether run2's IN FFT amplitude recovers to ~20 mm after the filter cleans the troughs.
  The dry run showed FFT_new ≈ FFT_old (14.4 mm) for run2. This might mean the depressed
  amplitude has a different root cause (genuine wave difference in that run, not just the
  processing artifact). Or it might be a bug in the dry-run FFT simulation.
- Whether the filter creates false positives on full-wind or low-frequency runs.
